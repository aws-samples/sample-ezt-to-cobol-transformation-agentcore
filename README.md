# BRE-Based Source-to-COBOL Translation Tool

An AI-powered system that converts mainframe Easytrieve (.ezt) and Assembly (.asm) code to COBOL using Business Rules Extraction (BRE) methodology, deployed on Amazon Bedrock AgentCore.

> **Disclaimer**: This project is sample code for demonstration and educational purposes only.
> It is not intended for production use without additional security review and testing.
> COBOL generated by this tool is produced by a large language model and must be reviewed,
> tested, and validated by qualified engineers before it is compiled or run against real data.

## Overview

This tool uses a **Business Rules Extraction (BRE)** methodology to translate legacy source code (Easytrieve or Assembly) to COBOL. Rather than doing a naive line-by-line translation, it extracts high-level business rules and uses them to generate clean, maintainable COBOL code. The pipeline runs as a Strands Agent on **Amazon Bedrock AgentCore**.

### Supported Source Languages

- **Easytrieve** (.ezt files)
- **Assembly** (.asm files)

### Target Users

Developers and organizations modernizing legacy mainframe code to COBOL for improved maintainability and readability.

## EZT-to-COBOL Quick Start

Complete step-by-step guide to convert Easytrieve files to COBOL.

### Prerequisites

- **Python 3.10+**
- **AWS CLI** installed, with credentials from `aws configure sso`, an `AWS_PROFILE`, or an AWS Identity and Access Management (IAM) role. Do not use long-term access keys stored in files.
- **AWS account** with Anthropic Claude model access enabled in the Amazon Bedrock console (Model access). The default model is Claude Sonnet 4.5.
- **Amazon S3 bucket** that you own, for pipeline input and output.
- **AWS Identity and Access Management (IAM) permissions** for the identity you run with, scoped to your own resources (least privilege). The identity needs to:
  - invoke the Amazon Bedrock models it uses (`bedrock:InvokeModel` and `bedrock:InvokeModelWithResponseStream`),
  - read and write objects in your Amazon S3 bucket, and
  - optionally write logs to Amazon CloudWatch Logs and publish Amazon CloudWatch metrics.

  Scope each permission to specific resources and avoid wildcard (`*`) resources wherever the service supports resource-level permissions. See [IAM security best practices](https://docs.aws.amazon.com/IAM/latest/UserGuide/best-practices.html). The Strands agent that routes your prompt to the pipeline tools also calls Amazon Bedrock. It uses the model set in `AGENT_MODEL_ID` (default: the same Claude Sonnet 4.5 `us.` inference profile as the pipeline).

### Example runtime IAM policy

Attach a policy like this to the local identity or AgentCore runtime role that runs the pipeline. Replace `123456789012` and `your-pipeline-bucket` before use. This policy can read source only from `input/`, write artifacts only to `outputs/`, write only to the pipeline log group and metric namespace, and invoke only the pinned Claude Sonnet 4.5 US inference profile and its foundation-model ARNs.

Create `/bedrock-agentcore/asm-to-cobol` before applying this policy. ### Step 1: Install Dependencies

```bash
# Create and activate virtual environment
python3 -m venv venv_agentcore
source venv_agentcore/bin/activate

# Install all dependencies
python -m pip install -r requirements.txt

# Optional: test dependencies
python -m pip install -r requirements-dev.txt
```

### Step 2: Create an S3 Bucket

```bash
aws s3 mb s3://your-bucket-name --region us-east-1
```

S3 bucket names are globally unique, so choose your own. The pipeline has no default bucket and will refuse to start without `PIPELINE_S3_BUCKET`.

### Step 3: Upload EZT Input Files to S3

```bash
# Upload all EZT files
aws s3 cp data/input/ezt/ s3://your-bucket-name/input/ezt/ --recursive

# Verify upload
aws s3 ls s3://your-bucket-name/input/ezt/
```

You should see your `.ezt` files listed (e.g., `Payroll.ezt`, `pgm4.ezt`, `report.ezt`, `summary.ezt`).

### Step 4: Configure Environment Variables

```bash
export AWS_REGION=us-east-1
export PIPELINE_S3_BUCKET=your-bucket-name
```

### Step 5: Verify LLM Configuration

Check `config/llm_config.yaml` has the correct model:

```yaml
llm:
  provider: "aws_bedrock"
  model: "us.anthropic.claude-sonnet-4-5-20250929-v1:0"
  max_tokens: 8192
  temperature: 0.0
  region: "us-east-1"
```

> **Note:** The model must be enabled in your Amazon Bedrock console under Model Access.
> Use the `us.` prefix for cross-region inference profiles (required for newer models).

### Step 6: Start the Agent (Terminal 1)

```bash
source venv_agentcore/bin/activate
export AWS_REGION=us-east-1
export PIPELINE_S3_BUCKET=your-bucket-name

python -m src.agentcore.app
```

The server prints very little. It is running when `curl -s http://127.0.0.1:8080/ping` returns `{"status":"Healthy",...}`. It listens on port 8080 on localhost only.

### Step 7: Invoke the Pipeline (Terminal 2)

Open a **second terminal** and run:

```bash
source venv_agentcore/bin/activate
export AWS_REGION=us-east-1
export PIPELINE_S3_BUCKET=your-bucket-name

# Process a single EZT file
curl -s -X POST http://localhost:8080/invocations \
  -H "Content-Type: application/json" \
  --max-time 900 \
  -d '{"prompt": "Process the Easytrieve file at input/ezt/Payroll.ezt"}'
```

> **Important:** The pipeline runs 5 LLM calls sequentially and can take 3-10 minutes per file.
> Use `--max-time 900` (15 min) to avoid client-side timeouts.

### Step 8: Process All Files (Batch)

```bash
for file in pgm4 Payroll report summary; do
  echo "Processing $file..."
  curl -s -X POST http://localhost:8080/invocations \
    -H "Content-Type: application/json" \
    --max-time 900 \
    -d "{\"prompt\": \"Process the Easytrieve file at input/ezt/${file}.ezt\"}"
  echo -e "\n---"
done
```

### Step 9: Check Results in S3

```bash
# List all generated artifact directories
aws s3 ls s3://your-bucket-name/outputs/

# Download all outputs locally
aws s3 cp s3://your-bucket-name/outputs/ ./outputs/ --recursive
```

### Output Structure

For each processed file, the pipeline produces:

```
s3://your-bucket-name/outputs/{program-name}-{source-type}-{key-hash}/
├── phase1_bre.json           # Business Rules Extraction document
├── phase2_spec.json          # Functional Specification
├── phase3_cobol.cbl          # Generated COBOL source code
├── phase4_validation.json    # Validation report with equivalence score
└── phase5_analysis.json      # Quality analysis and recommendations
```

For example, `input/ezt/Payroll.ezt` is written below a prefix such as `outputs/Payroll-easytrieve-a1b2c3d4e5f6/`. The final 12 characters are a SHA-256 prefix of the validated S3 input key, so same-named programs from different source types or folders cannot overwrite one another. The pipeline response includes every exact artifact path.

## Key Features

### 1. Business Rules Extraction (BRE)
- Identifies conditional logic, calculations, and data transformations
- Maps source fields to meaningful business data fields
- Documents business purpose and logic in natural language
- Provides source location tracking for traceability

### 2. Functional Specification Generation
- Designs COBOL-compatible data structures with proper PIC clauses
- Follows COBOL naming conventions and level numbering
- Defines process flows that implement all business rules

### 3. COBOL Code Generation
- Generates syntactically valid COBOL from BRE and specifications
- Implements all business rules as COBOL procedures
- Includes traceability comments linking code to business rules

### 4. Multi-Level Validation
- **Syntax Check** (20%): Verifies COBOL syntax validity
- **Structure Check** (20%): Compares program structure
- **Logic Check** (30%): Verifies conditional logic and calculations
- **Data Flow Check** (30%): Verifies field-to-variable mappings
- **BRE Coverage** (10% bonus): Ensures all business rules are implemented
- **Spec Compliance** (10% bonus): Verifies code follows specifications

### 5. Feedback Analysis
- Quality assessment (excellent/good/fair/poor)
- Specific improvement areas by category
- Actionable recommendations with examples

## BRE-Based Approach

### Why BRE Instead of IR?

| Aspect | IR-Based Approach | BRE-Based Approach |
|--------|-------------------|-------------------|
| **Intermediate Format** | Low-level IR (registers, operations) | High-level business rules |
| **Understandability** | Technical, hard to review | Business-focused, easy to review |
| **Validation** | Structural only | Multi-level including business logic |
| **Maintainability** | Difficult to modify | Easier with clear business rules |
| **Review Process** | Requires source language expertise | Business analysts can review |

## Pipeline Architecture

The pipeline runs as a Strands Agent on AgentCore. Each phase is exposed as a `@tool`:

```
Source Code (.ezt or .asm)
     │
     ▼
Phase 1: extract_bre         → BRE document (JSON)
     │
     ▼
Phase 2: generate_spec       → Functional specification (JSON)
     │
     ▼
Phase 3: generate_cobol      → COBOL source code (.cbl)
     │
     ▼
Phase 4: validate_translation → Validation report (JSON)
     │
     ▼
Phase 5: analyze_results     → Analysis report (JSON)
```

### AgentCore Tools

| Tool | Description |
|------|-------------|
| `extract_bre` | Extract business rules from source code |
| `generate_spec` | Generate functional spec from BRE document |
| `generate_cobol` | Generate COBOL from source + BRE + spec |
| `validate_translation` | Validate translation accuracy |
| `analyze_results` | Analyze results and generate feedback |
| `process_asm_from_s3` | End-to-end pipeline for an ASM file in S3 |
| `process_ezt_from_s3` | End-to-end pipeline for an EZT file in S3 |
| `process_source_from_s3` | Auto-detect source type and run pipeline |

### Observability

Pipeline phases emit structured logs and Amazon CloudWatch metrics:
- **Log group**: `/bedrock-agentcore/asm-to-cobol`
- **Metrics namespace**: `ASMtoCOBOL/Pipeline`
- Phase latency, error counts, and structured error traces

## Deploy to Amazon Bedrock AgentCore

Running locally (above) does not need the `agentcore` CLI. To deploy the agent to AWS, install the AgentCore starter toolkit, which provides it:

```bash
python -m pip install bedrock-agentcore-starter-toolkit==0.3.14

agentcore configure --entrypoint src/agentcore/app.py
agentcore launch
agentcore invoke '{"prompt": "Process the Easytrieve file at input/ezt/pgm4.ezt"}'
```

- The toolkit version above is the latest release at the time of writing. It is pinned, but it has not been tested with this project, so review it before use. Check it with `pip-audit` and update deliberately.
- `agentcore configure` asks for your own execution role and region, then writes `.bedrock_agentcore.yaml`. That file holds your AWS account ID, role and runtime ARNs, and local paths, so it is **gitignored and must not be committed or shared**.
- The deployed runtime's execution role needs the same permissions described in [Prerequisites](#prerequisites), and `PIPELINE_S3_BUCKET` must be set in the runtime environment.
- The `agentcore invoke` CLI has a 180s timeout. Pipeline runs take longer, so use the AWS SDK or `curl` for large files.
- See the [AgentCore starter toolkit documentation](https://github.com/aws/bedrock-agentcore-starter-toolkit) for current options.

## Configuration

### LLM Configuration

Edit `config/llm_config.yaml`:

```yaml
llm:
  provider: aws_bedrock
  model: us.anthropic.claude-sonnet-4-5-20250929-v1:0
  max_tokens: 8192
  temperature: 0.0
  region: us-east-1
```

Environment variable overrides are supported:
- `AWS_REGION` — override region
- `LLM_MODEL` — override model
- `LLM_MAX_TOKENS` — override max tokens
- `LLM_TEMPERATURE` — override temperature
- `LLM_CONFIG_PATH` — override config file path
- `PIPELINE_S3_BUCKET` — S3 bucket for input/output (required, no default)
- `PIPELINE_MAX_SOURCE_BYTES` — maximum source file size read from S3 (default 1000000)
- `AGENT_MODEL_ID` — model used by the routing agent (default `us.anthropic.claude-sonnet-4-5-20250929-v1:0`)

### Supported Models

| Model | ID |
|-------|-----|
| Claude Sonnet 4.5 (default, tested) | `us.anthropic.claude-sonnet-4-5-20250929-v1:0` |

> Other Claude models enabled in your account can be used by changing `model`. Models are retired over time: a `ResourceNotFoundException` that mentions end of life means you must switch to a current model ID.
>
> Use the `us.` prefix for cross-region inference profiles (required for on-demand invocation of newer models).

### AWS Credentials

This project never reads or stores access keys. Credentials resolve through the standard boto3 chain: `aws configure sso`, `AWS_PROFILE`, an IAM role, or environment variables set by your tooling. `config/settings.env` (gitignored) may hold non-secret overrides such as `AWS_REGION`. Any `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, or `AWS_SESSION_TOKEN` entries in it are ignored.

## Security

- Source files are sent to Amazon Bedrock inside prompts. Treat inputs as untrusted: a source file can contain instructions that influence the model (prompt injection).
- Generated COBOL and validation scores are LLM output. Validation is done by an LLM too, so it is not a security or correctness gate. Review and test generated code before compiling or running it.
- Do not commit `.bedrock_agentcore.yaml`, `config/*.env`, or any credentials.
- See [SECURITY.md](SECURITY.md) for reporting and production guidance.

## Equivalence Score

Ranges from **0.0 to 1.2** with a passing threshold of **0.7**.

```
Base Score = (Syntax × 0.2) + (Structure × 0.2) + (Logic × 0.3) + (Data Flow × 0.3)
Bonus      = (BRE Coverage × 0.1) + (Spec Compliance × 0.1)
Total      = Base + Bonus
```

| Score Range | Quality Level | Description |
|-------------|---------------|-------------|
| 0.9 - 1.2 | Excellent | Strong match, still requires human review |
| 0.7 - 0.89 | Good | Minor improvements needed |
| 0.5 - 0.69 | Fair | Significant improvements needed |
| < 0.5 | Poor | Requires rework |

## Troubleshooting

### "command not found: agentcore"
The `agentcore` CLI is provided by the separate `bedrock-agentcore-starter-toolkit` package, not by `bedrock-agentcore`. Install it only if you want to deploy. For local runs use `python -m src.agentcore.app`.

### "externally-managed-environment" pip error
Use `python -m pip` instead of `pip3`:
```bash
python -m pip install -r requirements.txt
```

### Client timeout (180s)
The `agentcore invoke` CLI has a 180s timeout. Use `curl` directly:
```bash
curl -s -X POST http://localhost:8080/invocations \
  -H "Content-Type: application/json" \
  --max-time 900 \
  -d '{"prompt": "..."}'
```

### "The provided model identifier is invalid"
- Verify the model is enabled in your [Bedrock Model Access](https://console.aws.amazon.com/bedrock/home#/modelaccess) console
- Use the `us.` prefix for cross-region inference profiles
- Ensure `AWS_REGION` matches the region where the model is enabled

### "on-demand throughput isn't supported"
The model requires a cross-region inference profile. Add the `us.` prefix:
```yaml
# ❌ Wrong
model: "anthropic.claude-sonnet-4-20250514-v1:0"

# ✅ Correct
model: "us.anthropic.claude-sonnet-4-20250514-v1:0"
```

### AWS Credentials Not Found
Configure credentials with `aws configure sso`, set `AWS_PROFILE`, or use an IAM role. Do not store access keys in project files.

### "S3 bucket not configured"
Set `PIPELINE_S3_BUCKET` to the name of your bucket before starting the server.

### `ResourceNotFoundException` mentioning end of life
The model in `config/llm_config.yaml` has been retired. Switch to a current model ID (see [Supported Models](#supported-models)).

### LLM Read Timeout
Large files may cause Bedrock to timeout. The client has built-in retry logic (3 attempts with 30s waits). If it persists, try a smaller file or check Bedrock service health.

### Low Validation Score
Review the analysis report:
```bash
aws s3 cp s3://your-bucket-name/outputs/{program}/phase5_analysis.json -
```
