# Security Policy

## Disclaimer

This project is provided as sample/educational code and is NOT intended for production use without
additional security hardening. COBOL produced by this tool is generated by a large language model and
must be reviewed, tested, and validated by qualified engineers before it is compiled or run against
real data. See "Production Hardening Recommendations" below.

## Reporting Vulnerabilities

If you discover a security vulnerability in this project, please report it by emailing
aws-security@amazon.com. Do not report security vulnerabilities through public issues.

## AWS Services Used

- **Amazon Bedrock** runs Anthropic Claude Sonnet 4.5 (`InvokeModel`) through the `us.` cross-Region
  inference profile to extract business rules, generate specifications, generate COBOL, and validate
  output. Requests may be processed in any US Region covered by the inference profile. The Strands
  agent that routes prompts to tools also calls Amazon Bedrock, using the model in `AGENT_MODEL_ID`
  (default: the same Claude Sonnet 4.5 `us.` inference profile).
- **Amazon S3** stores the input source files and the pipeline outputs, in a bucket you provide through
  `PIPELINE_S3_BUCKET`.
- **Amazon CloudWatch** (Logs and Metrics) receives phase logs and latency/error metrics
  (log group `/bedrock-agentcore/asm-to-cobol`, namespace `ASMtoCOBOL/Pipeline`). These calls are
  optional and fail soft.
- **Amazon Bedrock AgentCore Runtime** hosts the agent, only if you choose to deploy it. Running locally
  with `python -m src.agentcore.app` does not use it.

This repository does not create AWS resources on its own. Deployment with the AgentCore toolkit creates
a runtime and execution role in your account.

## Prerequisites and Permissions

- An AWS account with Amazon Bedrock model access enabled for Anthropic Claude Sonnet 4.5
- An IAM principal (preferably an AWS IAM Identity Center / SSO role) with least-privilege access. See the
  guidance in [README.md](README.md#prerequisites):
  - `bedrock:InvokeModel` and `bedrock:InvokeModelWithResponseStream` on the specific models in use
  - `s3:GetObject` and `s3:PutObject` on your pipeline bucket only
  - Optional CloudWatch Logs and `cloudwatch:PutMetricData` for observability
- Python 3.10+ and the pinned dependencies in `requirements.txt`
- Credentials supplied through the standard AWS credential chain (`aws configure sso`, `AWS_PROFILE`,
  or an IAM role). This project never reads or stores access keys. Do not put long-term access keys in
  project files.

## Files That Must Not Be Committed

- `.bedrock_agentcore.yaml` is generated by `agentcore configure`. It contains your AWS account ID,
  role and runtime ARNs, and local paths. It is listed in `.gitignore`.
- `config/*.env` files. Any AWS credential variables in them are ignored by the application, but the
  files are still gitignored.

## Known Security Considerations

| Item | Category | Rationale |
|------|----------|-----------|
| Source code is sent to the LLM as-is. Instructions inside a source file can influence generated COBOL and validation results (prompt injection). | Security Debt | Core function of the tool. Output is never executed by the tool, so human review is required before use. |
| LLM-based validation is not an acceptance test. | Security Debt | The same kind of model that generates the code also scores it, so scores can be wrong or manipulated. |
| Users can send free-form prompts to the Strands agent, which chooses which tool to call. | Security Debt | The agent can only call the pipeline tools and read S3 keys in the configured bucket. Restrict who can invoke the runtime. |
| Broad `except Exception` handlers may return default results on failure. | Security Debt, Non-Blocking | To be narrowed to specific exception types. |
| Pipeline outputs in S3 and local `outputs/` contain excerpts of the input source code. | Consideration | Treat as sensitive as the input source. Do not share outputs outside the authorized team. |

## Production Hardening Recommendations

- **Prompt-injection controls**: Wrap source in explicit delimiters, add a system prompt stating that the
  delimited content is data, and apply Amazon Bedrock Guardrails (prompt-attack filter) to all
  `InvokeModel` calls.
- **Acceptance testing**: Gate generated COBOL with human code review plus deterministic regression tests
  (run the original and generated programs on the same input datasets and compare outputs).
- **Least privilege**: Scope the execution role to the specific model ARNs and the single S3 bucket. Use an
  SSO or role session, never IAM user keys.
- **Access control**: Put authentication in front of the deployed runtime (AgentCore supports JWT/OAuth
  authorizers) so only authorized users can start pipeline runs.
- **S3**: Enable default encryption, block public access, versioning, and a lifecycle rule on the pipeline
  bucket. Use separate prefixes per team or sensitivity level.
- **Logging**: Keep `botocore`/`urllib3` at WARNING or above (already set in `src/agentcore/app.py`). Set a
  retention period on the CloudWatch log group.
- **Data residency**: If source code must stay in one Region, replace the `us.` inference profile with a
  single-Region model ID in `config/llm_config.yaml`, and set `AGENT_MODEL_ID` to the same model.
- **Auditing**: Enable AWS CloudTrail to record Amazon Bedrock and S3 API calls. Consider Bedrock model
  invocation logging to an encrypted, access-controlled destination.
- **Dependencies**: Keep `requirements.txt` pinned and run `pip-audit -r requirements.txt` before each
  release.

## Resource Cleanup

See [Cleanup in README.md](README.md#cleanup). In short: remove the objects (and the bucket, if you
created it for this project) from S3, delete the AgentCore runtime and its CloudWatch log group if you
deployed, and delete local output folders and virtual environments.
